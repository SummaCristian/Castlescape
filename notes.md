# Notes about the project
Here we are going to list all interesting/weird things we found/implemented/discovered during development.

This will help us remember them for the final oral presentation.

## Camera
- Input handling comes bundled in `Starter.hpp`. Everything is hardcoded. WASD for movement, arrow keys for camera yaw/pitch, and mouse cursor support as well. Mouse is ONLY supported with the **left button pressed**. We can't change that without either editing the Starter file (we can't!) or re-implementing it ourselves, which may not work with the prof's version of Starter...
- Gravity is handled in the camera. It's optional: allows flying as a cheat/debug option
- Jump is bound to spacebar, which `Starter.hpp` already wires to the `fire` output of `getSixAxis`, so no changes were needed there. It's a simple upward velocity impulse, gated behind its own optional flag (like the other cheats), and only triggers on a fresh key press while grounded.
- "Grounded" can't be inferred just by checking if vertical velocity is exactly `0`: looking up/down while walking bleeds a bit of the camera's front vector into vertical movement, which can leave you standing but with nonzero velocity. Ground contact is instead computed directly against the colliders every frame.
- Sprint is bound to Ctrl (not wired by `Starter.hpp`, so polled directly via `glfwGetKey`), gated behind its own flag too. Can only be started while grounded, but once sprinting, releasing Ctrl always stops it immediately even mid-air, since our movement isn't a persisted velocity. There's no "momentum" to preserve through a jump.

## Colliders
- Floor collider has `AABB`-based ground detection, provided by `Colliders.hpp` and `Scene.hpp` files. Simply saying 
`"collider": "AABB"` in the `scene.json` file will apply ground detection to whatever model is used as floor. 
- Collision detection is optional, controlled by a flag. Allows to have a `no-clip` cheat/debug option

## Cheats / debug toggles
- All debug/cheat flags (`gravityEnabled`, `collisionEnabled`, `jumpEnabled`, `sprintEnabled`) are grouped into one `CheatFlags` struct, held as a single `cheats` member on the app class, instead of being loose booleans scattered among the camera/physics state.
- No persistence on purpose: it's a plain struct with default member initializers, so it just resets to the "legit" defaults (everything `true`, i.e. cheats off) every time the app starts. No config file, no serialization needed.
- Grouping them like this makes them easy to find as a block, easy to reset all at once, and gives a natural place to hang a future debug UI or keybind toggles off of (e.g. iterate/reflect over the struct's fields) without polluting the rest of the class's member list.
- Call sites read through the struct, e.g. `if(cheats.gravityEnabled)`, `if(cheats.collisionEnabled)`, `if(cheats.jumpEnabled)`, `if(!cheats.sprintEnabled || !ctrlHeld)`.
- The numeric tuning behind those cheats (`moveSpeed`, `sprintMultiplier`, `jumpSpeed`, `gravity`) lives in a separate `MovementParams` struct (`movement` member), not in `CheatFlags`. Reasoning: those bools answer "is this cheat on/off", these floats answer "how strong is it", different concern, so a different struct, even though both sit next to each other on the class and follow the same no-persistence pattern.
- Jump does nothing with gravity turned off, on purpose: jump only sets an upward velocity, and that velocity only ever turns into actual movement inside the `gravityEnabled` branch of `GameLogic()`. With gravity off it gets reset to `0` the same frame. Vertical movement without gravity goes through R/F (direct fly up/down) instead.

## Cheat HUD (`CheatHud.hpp` / `UiQuad.hpp`)
- Toggle menu for the four cheats above, bound to `L`. Opens/closes on `L`, navigable with Up/Down + Enter or the mouse, freezes the game (camera and physics both) while open.
- The skeleton's only 2D drawing primitive is `TextMaker` (glyph quads from a font atlas), and there's no filled rectangle in its printable ASCII range. So the toggle rows are plain `TextMaker` text, but the panel background and the selection-highlight bar needed a second, minimal pipeline of our own (`UiQuad.hpp`): flat-colored quads, no textures or descriptor sets, just a push-constant color, modeled directly on how `TextMaker` builds and submits its own pipeline. No changes to `Starter.hpp` anywhere in this feature.
- Mouse look is gated behind holding the left button in `Starter.hpp`'s `getSixAxis`, not a captured cursor, so the mouse was already free to use for HUD hit-testing. The only conflict: `getSixAxis` also reads that same left click as a drag-look input. Fixed by reading the HUD's own click first (see the sticky-mouse-button gotcha below) and, if the HUD is open, zeroing out the `m`/`r`/`fire` values `getSixAxis` returns before they reach the camera.
- `getSixAxis` turns on `GLFW_STICKY_MOUSE_BUTTONS`, which makes `glfwGetMouseButton` a one-shot read: it reports a press once, then reads back as released until the button is physically released and pressed again. Whoever polls the mouse button first each frame gets that one true reading. That's why `hud.update()` is called before `getSixAxis()` in `GameLogic()`, not after.
- Depth test gotcha: `Pipeline::create()` hardcodes depth test and depth write on for every pipeline, with no way to turn it off from outside `Starter.hpp`. The background panel and the highlight bar both sit at `z=0` and overlap on screen, so with the default `LESS` compare op the highlight (drawn second) failed the depth test against the depth the background had just written at that same `z`, and silently never appeared. Fixed with `VK_COMPARE_OP_LESS_OR_EQUAL`, the same fix `TextMaker` already uses for its own overlapping same-z glyph quads.
- Buffer-lifetime gotcha: once a named command buffer is submitted through `BaseProject::submitCommandBuffer`, `Starter.hpp` dereferences its "current" entry unconditionally every frame from then on, with no supported way to detach it and later resubmit under the same name. So `UiQuad` can never just submit "nothing" while the HUD is hidden: it always keeps at least one real (if geometrically empty/unused) quad in its mesh, since `Model::initMesh` also flatly refuses a zero-size buffer.
- Resize gotcha: `CheatHud::renderRows()` converts each row's pixel position into a fixed NDC anchor before calling `TextMaker::print()`. `UiQuad`'s rects stay in pixel space and get reconverted on every mesh rebuild, so they track a resize automatically, but `TextMaker::resizeScreen()` just rebuilds from whatever NDC anchor was already baked in, so text silently stayed positioned for the old window size after a resize. Fixed by having `CheatHud` remember the last screen size it rendered for and force a fresh render (with fresh anchors) whenever that size changes while the HUD is open.
- Panel size is computed, not guessed: `CheatHud::computeLayout()` calls `TextMaker::measureText()` to get the actual rendered width/height of the title and of each row's label + `[ON]`/`[OFF]` state, then sizes the background panel to exactly fit that. `measureText` takes a `fontId` rather than the `(FontFace, Bold, Italic, Small)` flags `print()` takes, so `computeLayout()` duplicates `print()`'s own formula for turning those flags into a `fontId`.
