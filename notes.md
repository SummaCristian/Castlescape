# Notes about the project
Here we are going to list all interesting/weird things we found/implemented/discovered during development.

This will help us remember them for the final oral presentation.

## Vertex format and normals (`VDposNormUV`)
- The skeleton ships a single vertex format carrying position and UV only, and its fragment shader rebuilt the normal per-fragment as `-normalize(cross(dFdx(fragPos), dFdy(fragPos)))`. That works, but the derivatives of the interpolated world position are constant across a triangle, so what it produces is a **face** normal: every mesh renders faceted regardless of how it was authored. Exactly the situation E06 slides 3-16 and L10 are about.
- Fixed by declaring a normal in the vertex layout (`VDposNormUV`: pos, normal, UV). Nothing else was needed on the loading side: `Starter.hpp` already looks for the glTF `NORMAL` accessor and copies it in as soon as `VD->Normal.hasIt` is true (it even prints a warning when the layout wants normals the file lacks). Verified on startup: all 14 models load silently, so the whole MGCG castle pack carries per-vertex normals.
- Normals can't ride the world matrix like positions do. Under a non-uniform scale `mMat` tilts them off the surface, so the UBO gained a third matrix, `nMat = inverse(transpose(mMat))`, and the vertex shader uses its upper-left `mat3`. This scene really does have a non-uniform instance (`road` is scaled `[1, 4, 1]`), so it isn't a theoretical precaution.
- `nMat` is a `mat4` in the UBO rather than a `mat3` on purpose: a `mat3` in a std140 uniform block is laid out as three separately 16-byte-aligned columns, i.e. the same 48 bytes but with padding rules that are easy to get subtly wrong from the C++ side. Passing a `mat4` and truncating in the shader costs 16 bytes and removes the whole class of bug.
- The interpolated normal is renormalized in the fragment shader. Linear interpolation across a triangle shortens the vector wherever the three corner normals diverge, which is precisely where a smooth surface needs it to be right.
- Shaders renamed to match what they now do, since both old names encoded the removed hack: `toChangeSimplePos.vert` to `PosNormUV.vert` (named after the vertex format, like the professor's own `PosNormUvTanWeights.vert`), `toChangeBlinnFromPos.frag` to `Blinn.frag` ("FromPos" meant the normal came from the position). The technique in `scene.json` went from `BlinnPos` to `Blinn` for the same reason. CMake globs the shader directory, so renames need no build-file change, only the two paths in `P.init`.
- The light model itself was deliberately left untouched in this step: same ambient constant, same `pow(HdotN, 150)` specular. The only change is where `N` comes from. Rewriting the BRDF properly along L09 (Lambert plus Blinn-Phong, and the point/spot light types) is the next step, kept as its own change so the two are separable.

## BRDF, first version: Lambert diffuse + Blinn specular (superseded)
*Kept deliberately. This was the state between the normals step and Cook-Torrance, and the reason for each move is worth being able to retrace: the professor's own ladder in L09 and E06 runs Lambert to Blinn to the advanced models, and we walked it in that order. The section below it describes what is actually in the shader now.*

- The starting shader computed `(albedo * NdotL + pow(HdotN, 150)) * radiance` in one expression. All the pieces of a Lambert-plus-Blinn model are in there, but flattened: no separation between the two terms, and no material anywhere, so the specular was pure white with a hardcoded exponent on every surface in the scene, from the flag to the stone. Restructured into an explicit `BRDF(N, L, V, mD, mS, specPower)` returning `diffuse + specular`, the form L09 slide 38 states.
- `mD`, the diffuse color, is the albedo texture, per fragment. `mS` (specular color) and `specPower` (specular exponent) are per-material constants, so they became data: `assets/scenes/materials.json`, read by `SceneMaterials.hpp`, one entry per **model**. Keyed by model rather than by instance because a material is a property of the surface, and four towers are the same stone; keying by instance would mean repeating the same numbers 23 times. `Instance::Mid` is already the model index, so the render loop looks the material up by integer and never hashes a string.
- The lantern (`light`) is the model that justifies `mS` existing at all. Dielectrics reflect the *lamp's* color, so their `mS` is grey; metals reflect their own, so brass gets `[0.55, 0.45, 0.25]` instead. That's L09 slide 69, and it's a difference no amount of albedo texture can produce, because it only shows up in the highlight.
- Why Blinn and not Phong: Phong builds the mirror-reflected ray `r` and uses `dot(r, V)`; Blinn uses the half vector `h = normalize(L + V)` and `dot(N, h)`, which approximates the same angle for less work and degrades more gracefully at grazing incidence. L09 slides 82-84.
- Both terms are clamped at zero. On a face turned away from the light the cosine is negative, and unclamped the formula would *subtract* light from the object (L09 slide 59).
- Tone mapping switched to the professor's own HDR function, `c / (Y(c) + 1)` with `Y` the luminance (L09 slide 45). The previous version divided each channel by itself, which desaturates: a bright red would drift towards white as it brightened. Dividing by a single luminance scalar compresses the range while keeping the hue.
- The sun's `lightColor` went from `(1,1,1) * 5.0` to `(1,1,1)`. The 5 was compensating for the old ad-hoc formula; a BRDF that returns values in [0,1] (L09 slide 42) paired with an HDR tone map doesn't need it. The honest consequence is that the scene is now visibly darker on the side facing away from the sun, because indirect light is still a 0.015 constant. Inflating the sun would only hide that; the hemispheric ambient term (E07) is what actually fixes it.
- The local UBO was bound `VK_SHADER_STAGE_VERTEX_BIT` because it only ever held matrices. Now that it also carries the material it has to be `VK_SHADER_STAGE_ALL_GRAPHICS`, and the block must be declared identically in both shaders: it's one buffer at one binding, not two.
- `vec3 mS; float specPower;` needs no explicit padding between them. std140 gives a `vec3` a 16-byte alignment and a 12-byte size, so a following `float` lands at offset 12 and fills the gap, in GLSL and in the C++ struct alike. Passing them as a `vec4` would have worked too but hides what the fourth component means.
- Naming convention, decided deliberately and still in force: the light-model quantities keep the short names L09 and E06 give them (`mD`, `mS`, `N`, `L`, `V`, `h`, and later `D`, `G`, `F`) inside the shader, so the code reads side by side with the slides, and everything outside the formula is spelled out. Two exceptions, both where a Greek letter would have cost more than it saved: the specular exponent was `specPower` rather than gamma, because that word already meant the display gamma in the same file, and the roughness is `roughness` rather than `rho`. A single transliterated Greek letter is worse than the word it stands for.
- `materials.json` keeps `//` comments, which `nlohmann::json` rejects by default. `SceneMaterials` reads it through `json::parse(ifs, nullptr, true, true)`, the last argument being `ignore_comments`. Hand-tuned numbers are worthless without a line saying what they represent, and unlike `colliders.json` (whose numbers were measured off the mesh) these were chosen by eye.

## The MGCG meshes have smoothed normals on hard edges (`flatNormals`)
- Symptom: every riser of the staircase, and every flat wall panel, shaded with a *gradient across it* instead of one constant value, so hard-edged geometry looked soft and smeared.
- A flat face lit by a direct light plus hemispheric ambient must be uniform: both terms depend only on `N`, which is constant on a flat face. A gradient therefore means `N` is varying across the face, which means the mesh's vertex normals were averaged across its hard edges.
- Confirmed rather than assumed, by rendering `N * 0.5 + 0.5` as the colour: flat normals would give each face one flat colour, and instead every face came out a gradient. The floor (`Plane.gltf`) was uniform green, so the problem is specific to the MGCG models, not the pipeline.
- This is exactly the case E06 slides 3-16 set up: a hard-edged solid needs its vertices **duplicated per face**, each copy carrying its own normal. Whoever exported these meshes averaged instead, which is right for a sphere and wrong for a staircase.
- Fix: a per-material `flatNormals` flag. When set, the shader derives the face's own normal from the derivatives of the world position, `normalize(cross(dFdx(fragPos), dFdy(fragPos)))` — the two derivatives lie in the triangle's plane, so their cross product is exactly perpendicular to it.
- Note this is the same computation the skeleton's starting shader used, but the situation is the opposite. Then it was the *only* normal available and it was applied to everything, so nothing could ever be smooth. Now it is a per-material choice, and the smooth path is the default.
- The cross product's sign depends on the triangle's winding, so it is oriented against the interpolated vertex normal: `dot(faceN, N) < 0 ? -faceN : faceN`. The averaged normal is unreliable in direction detail but perfectly good at saying which side is outward.
- Set on `castleSteps` only. It must not be global: the towers are cylinders approximated by flat facets, and they *want* the averaged normals they shipped with. Deciding it per model is the whole point of it being a material parameter.

## The double gamma correction (a real bug, inherited from the skeleton)
- Symptom: every upward-facing surface in the castle blew out to flat white while the walls went dark and muddy, and curved surfaces showed no shading gradient at all. It looked like a lighting bug and wasn't.
- The skeleton's starting shader read the albedo as `pow(texture(albedoMap, fragUV).rgb, vec3(2.2))` and wrote its result as `pow(color, vec3(1.0/2.2))`, i.e. it converted sRGB to linear on the way in and back on the way out by hand. Both conversions were already being done by the hardware:
  - `Texture::init` in `Starter.hpp` defaults to `VK_FORMAT_R8G8B8A8_SRGB`, and an sRGB image view means the *sampler* returns linear values. The manual `pow(2.2)` was a second decode.
  - `chooseSwapSurfaceFormat` prefers `VK_FORMAT_B8G8R8A8_SRGB`, and an sRGB render target means the hardware encodes linear to sRGB on write. The manual `pow(1/2.2)` was a second encode.
- Why it looks the way it does rather than simply cancelling out: the two extra operations sit at opposite ends of the pipeline with all the lighting maths in between. A mid-grey texel at 0.5 comes out of the sampler at 0.21 and is then crushed to 0.03, while a white texel at 1.0 stays 1.0 (since 1 to any power is 1). So the texture's dark and mid tones collapse towards black and only the white patches survive, which is exactly the flat-white-tops-and-muddy-walls look. Meanwhile the extra encode on the output re-brightens the *lighting* term non-linearly, flattening the shading gradients that should reveal a curved surface.
- Fix: delete both `pow()` calls and let the hardware do its job. Sample the texture raw, write the tone-mapped colour raw.
- Worth knowing for the oral, because it is the sort of thing that looks like an art problem and is actually a colour-space problem. The rule: **do the conversion once**. If the format ends in `_SRGB`, the hardware is already doing it, and doing it again in the shader is not a stylistic choice, it is a bug.
- How it was found: rendering the albedo alone, with all lighting bypassed. The white patches survived that test, which proved the lighting was not producing them and pointed straight at the texture path. Bisecting a shader by outputting an intermediate value is the cheapest debugging tool there is.

## BRDF, current: Cook-Torrance with GGX (`CookTorrance.frag`)
- The specular is now a microfacet model instead of a curve chosen because it looked right. The surface is treated as a crowd of microscopic perfect mirrors; the model never draws them, it describes statistically how many face which way. For a given light and viewer, only the facets whose normal is exactly `h` can carry light from one to the other, so "how bright is the highlight" turns into "what fraction of the facets is oriented along `h`". That fraction is D.
- Three terms, E06 slides 38-47, and the useful way to hold them is by what breaks without each:
  - **D**, the GGX distribution, is the highlight itself. Remove it and there is no highlight at all. Roughness enters here, widening the lobe.
  - **G**, the geometric term, accounts for microfacets shadowing each other. Remove it and rough surfaces go absurdly bright at grazing angles. It takes no parameters, only angles.
  - **F**, Fresnel via Schlick, is the fraction reflected rather than transmitted, growing from `F0` head-on to 1 at the horizon. Remove it and you lose the single most recognisable real-world effect in the set: that every matte surface turns into a mirror when you look along it. Blinn has no counterpart to this at all.
- Why GGX for D: the long tail. A narrow core fading into a wide halo, which is how real surfaces behave, instead of Blinn's sharper cutoff. E06 slide 49 leaves the GGX expression "for exercise", so this is assigned material rather than something off-piste.
- `fr = clamp(N·L) * (k * mD + (1-k) * specular)`. The two halves are **interpolated** by `k`, not added. Adding both at full strength lets a surface return more light than it received; interpolating keeps the total in check, which is what E06 slide 38 means by handling the two components in a physically accurate way. It is also why metals look right: a metal is `k` near zero, because light does not enter it and so nothing comes back out diffusely.
- The `4 * (N·L) * (N·V)` denominator is not a fudge factor. It is the geometric normalisation converting from the area of the microfacets to the area of the surface carrying them. Worth being ready for as a question, because it is the one part of the formula that looks arbitrary and isn't.
- Guarded with `max(..., 0.0001)`. The denominator hits zero exactly at the silhouette, and although the whole term is multiplied by `N·L` immediately after (so the answer is zero there anyway), `inf * 0` is a NaN, and a NaN spreads through everything it touches.
- Material parameters went from `mS` + specular exponent to `mS` + `roughness` + `F0` + `k`. Note `mS` **stays**: in the professor's formulation the specular color and the Fresnel base reflectance are separate parameters, unlike the modern PBR convention that folds the color into an RGB `F0`. Following the slides here, since being able to read our code next to them is the point.
- The parameters are easier to author than what they replaced, which was the unexpected part. `F0` is ~0.04 for *every* dielectric, so it is copied rather than chosen; `roughness` runs 0 to 1 with a physical meaning you can estimate by looking at the object. The old specular exponent had no scale to anchor to, so 24 versus 150 was pure trial and error.
- `roughness` is clamped to a minimum of 0.03 at load, not in the shader. At exactly 0 the GGX denominator vanishes (a perfect mirror has all its facets in one direction, so the lobe has no width), and that is a data error, better caught once at load than guarded on every fragment.
- The shader and technique were renamed `Blinn` to `CookTorrance`, same discipline as the two earlier renames: the old name described a model that is no longer in the file.
- Oren-Nayar was deliberately **not** folded in. E06 slide 38 specifies Lambert for Cook-Torrance's diffuse half, and swapping in a different diffuse model would quietly stop being the model the slides describe. It belongs as its own technique, where it would actually earn its keep on the ground and the flag: it exists for retroreflective materials like clay, dirt and cloth (E06 slides 23-27), which is exactly what those two are.

## Light types: direct, point, spot (`SceneLights.hpp` / `lights.json`)
- The scene had exactly one light, a direct one, with its direction computed inline in `updateUniformBuffer` and its color hardcoded next to it. All three types L09 presents now exist, and they live in `assets/scenes/lights.json` for the same reason the colliders and the materials do: they are numbers that get tuned by looking at the result.
- The fragment shader's inner loop is now literally the rendering equation for scanline rendering: a sum over the sources of radiance times BRDF. What makes that sum legitimate is the clamp inside the BRDF from the previous step. Every term is non-negative, so a light can only ever *add* light. Without the clamp a lantern behind a wall would contribute a negative amount and cancel out part of what the sun put there, and the bug would look like objects getting darker as you bring a light closer.
- The three types differ in only two functions, `lightDirection()` and `lightRadiance()`, and the BRDF never knows which kind it is being handed. That is the structure L09 slide 31 describes: a spot is not a new light model, it is a point light multiplied by a cone term.
- Direct lights have no position and no decay: the source is infinitely far away, so every point in the scene sees it from the same direction. Point and spot aim at the lamp, so their direction changes across a surface, which is exactly why a point light wraps around a barrel and the sun does not.
- Decay is `(g / |p - x|)^beta` (L09 slides 22-23), with both numbers authored. `beta` is deliberately not the physically correct 2: with no real indirect lighting, inverse-square falloff reads as far too dark, which is the caveat the professor puts on slide 21 himself. The lanterns run at 1.4.
- Spot direction sign, worth being explicit about because it is easy to get backwards. The slides write the cone term with `lx`, the vector pointing *towards* the light. `dir` in our data file is instead the direction the lamp *points*, so that a lamp aimed at the floor is written `[0,-1,0]`, which is what anyone would expect to write. The shader therefore dots `-lightDirection()` against it. Same formula, one sign, chosen so the data file reads naturally.
- Cone angles are authored as **full** angles in degrees, because that is how a beam width is normally described, and converted to the cosine of the half angle at load time (L09 slide 29). Doing it once in `SceneLights::init` rather than per fragment also keeps two `cos()` calls out of the inner loop.
- The lights are a fixed-size array of `MAX_LIGHTS` plus a live `lightCount`. A uniform block needs a size known when the pipeline is built, so a variable-length array is not an option; the buffer is always 16 lights long and the count says how much of it is real.
- `MAX_LIGHTS` and the `LIGHT_*` tags are defined **once**, in `include/custom/LightConstants.glsl`, which both `SceneLights.hpp` and `Blinn.frag` `#include` by the same path. They started out written twice with a comment asking the reader to keep them in step, which is not a mechanism: change one side only and nothing complains, the C++ struct and the GLSL block silently stop describing the same bytes, and the symptom is wrong lighting rather than an error. Three things make the shared include work:
  - the file contains **only preprocessor directives**, the one syntax both languages agree on. A `const int` would compile in exactly one of the two. It also has to be a `#define` on the GLSL side regardless, since it sizes an array;
  - CMake passes glslc the same `-I source/include` the C++ compiler gets, so the `#include` line is spelled identically in both;
  - the shader enables `GL_GOOGLE_include_directive`, glslc's `#include` support. Core GLSL has no include at all, which is why this looked impossible at first.
- Those shared headers are also listed in each shader's CMake `DEPENDS`, or editing one would recompile nothing: glslc emits no dependency information for CMake to consume. It is deliberately coarse, every shader depends on every `.glsl` in `custom/`, which costs a full shader rebuild (eight small files, well under a second) in exchange for never missing one.
- `LightData` reuses the `vec3`-then-`float` std140 idiom from the material: three such pairs plus two trailing scalars, 56 bytes used, rounded to 64 by the struct's 16-byte alignment, identically in GLSL and C++.
- A light's position can be written explicitly or anchored to a scene.json instance with `"instance"` plus `"offset"`, which is what the gate lanterns use: move the lantern in scene.json and its flame follows. The offset is in **world** units rather than model-local ones, deliberately, since these models are Z-up and rotated by the scene, so local coordinates would need that correction applied by hand to every number. World units are also what the Show Coordinates overlay reads out, which is how the values get tuned.
- The 3.5 offset that puts the flame in the lamp head instead of at the foot of the post is not a guess: the lantern mesh measures 3.80 tall and 0.39 wide. Measured by temporarily giving the model an `"collider": "AABB"` in scene.json and printing `getExtents()`, then reverting both. Cheaper than the decrypt-the-MGCG route used for the staircase, and enough when all you need is a bounding box.
- The sun's sweep across the sky survived the move to data as an `orbitSpeed` field, since it was behaviour worth keeping but not worth hardcoding. The 45-degree tilt is baked into the authored direction and the orbit only sweeps it around the world up axis, which is exactly what the old inline `rotate * rotate` did.

## Indirect lighting: hemispheric ambient (E07)
- The project rules make indirect lighting mandatory and say a constant ambient term barely counts. Ours was `0.015 * mD`, i.e. exactly that constant. It is now the hemispheric model of E07 slides 47-54, which is the smallest step that is genuinely a model rather than a fudge factor.
- The idea in one line: a constant ambient claims light arrives equally from every direction, and outdoors that is plainly false. A surface facing up sees the sky, one facing down sees the ground, and those are different colors. So the term is made to depend on the normal.
- `lA = mix(lower, upper, (dot(N, ambientDir) + 1) / 2)`, then multiplied by `mD`. Aligned with `ambientDir` gives pure sky, opposite gives pure ground, perpendicular gives half of each. The `(x+1)/2` is just remapping a dot product's -1..1 into a 0..1 weight. Slide 53's own worked example (¾ sky + ¼ ground) falls out of it, which is a quick way to check the formula is the right way round.
- The multiplication by `mD` is the ambient BRDF term. E06 slide 758 defines it as a constant, the "ambient light reflection", and for a diffuse surface that constant is its base color: indirect light gets reflected the same way direct light does.
- Authored in `lights.json` next to the light sources, because it *is* lighting. Cool and dim above (`0.10, 0.13, 0.20`), warmer and darker below (`0.07, 0.055, 0.04`): skylight is blue, bounce off a dirt courtyard is brown. Setting the two to the same color would throw away the whole point and silently put a constant ambient back.
- Cost: one dot product and one `mix` over uniforms, no texture, no extra pass. That is the argument for doing this before IBL (E08), which needs a filtered cube map and a lot more machinery for the next increment in quality.
- The sun's orbit is parked (`orbitSpeed: 0`) rather than running. With no shadow mapping a direct light keeps shining once it passes below the horizon, lighting every upward-facing surface from underneath, which reads as the ground glowing at night. Three ways out: clamp the sun's contribution as it crosses the horizon, implement shadow maps (lab E07), or simply do not let it get there. The third costs one number and is honest about what the renderer can currently do, so that is the one taken. The orbit machinery stays in `SceneLights`, so re-enabling it is a data change.
- Its elevation is ~55 degrees, deliberately not straight down. A sun at `[0,-1,0]` would give every vertical wall in the castle `dot(N, L) = 0`, so the whole castle would be lit by ambient alone. The small X component tilts it off the scene's axis of symmetry so the east and west towers aren't lit identically.

## Camera
- Input handling comes bundled in `Starter.hpp`. Everything is hardcoded. WASD for movement, arrow keys for camera yaw/pitch, and mouse cursor support as well. Mouse is ONLY supported with the **left button pressed**. We can't change that without either editing the Starter file (we can't!) or re-implementing it ourselves, which may not work with the prof's version of Starter...
- Gravity is handled in the camera. It's optional: allows flying as a cheat/debug option
- Jump is bound to spacebar, which `Starter.hpp` already wires to the `fire` output of `getSixAxis`, so no changes were needed there. It's a simple upward velocity impulse, gated behind its own optional flag (like the other cheats), and only triggers on a fresh key press while grounded.
- "Grounded" can't be inferred just by checking if vertical velocity is exactly `0`: looking up/down while walking bleeds a bit of the camera's front vector into vertical movement, which can leave you standing but with nonzero velocity. Ground contact is instead computed directly against the colliders every frame.
- Sprint is bound to Ctrl (not wired by `Starter.hpp`, so polled directly via `glfwGetKey`), gated behind its own flag too. Can only be started while grounded, but once sprinting, releasing Ctrl always stops it immediately even mid-air, since our movement isn't a persisted velocity. There's no "momentum" to preserve through a jump.

## Colliders
- Floor collider has `AABB`-based ground detection, provided by `Colliders.hpp` and `Scene.hpp` files. Simply saying 
`"collider": "AABB"` in the `scene.json` file will apply ground detection to whatever model is used as floor. 
- Collision detection is optional, controlled by a flag. Allows to have a `no-clip` cheat/debug option
- Collision runs as two passes over the same collider list: a horizontal one that pushes the player out of walls, and a vertical one that clamps the feet onto the tallest standable surface. They have to agree on what counts as "a step you can walk onto" or they cancel each other out, which is exactly what happened: the wall pass rejected anything taller than its own `VERTICAL_MARGIN` (0.1) while the ground pass was willing to lift the player up to `MAX_STEP_HEIGHT` (0.5). The player got pushed away from a low crate before the ground pass ever saw it, so that 0.1-0.5 window was dead and *every* obstacle behaved like a wall. Fixed by making the wall pass skip anything at or below `feetY + MAX_STEP_HEIGHT` and by promoting `MAX_STEP_HEIGHT` to a single shared constant on the class, so the two passes can't drift apart again.
- After that split, the feet-side half of the wall pass's old `verticallyInside` test is redundant (surviving the step check already means the collider's top is well above the feet). Only the head-side test is left, and it's what lets the player walk under the gate's lintel.

## Authored collision geometry (`SceneColliders.hpp` / `colliders.json`)
- `"collider": "AABB"` in scene.json auto-fits **one** box around the whole model. Right for solid box-shaped meshes (walls, towers, crates), wrong for anything hollow or profiled: the box fills the gate's archway, and it caps the staircase at the height of its *top* step, so both become walls. Those models get no `"collider"` at all and their collision geometry is authored as boxes in `assets/scenes/colliders.json` instead. The usual render-geometry / collision-geometry split: the collision version is far coarser, and lives in data rather than as magic numbers in `main.cpp` (which is where the gate's three boxes started out).
- Boxes are authored in the **model's local space** and get the **instance's** world matrix applied, so one authored set follows any translate/rotate/scale scene.json gives that instance, for every instance of that model, with no duplicated numbers.
- These MGCG models are Z-up with the origin at the base, so local "up" is **-Z** (it only becomes +Y after the usual `eulerAngles: [90, ...]`). That's why the ramp's `rise` runs from 0.0 down to -9.0.
- Two entry types: `"boxes"` (explicit AABBs, used by the gate) and `"ramps"` (sloped walkable surfaces, used by the staircase). A first version also expanded a flight into one box per tread; it worked, but see the next bullet for why it was dropped rather than kept alongside.
- Why the ramp won for this staircase: the steps are enormous next to the player. Riser 0.45 against a 1.8-tall body is a quarter of his height gained every 0.8 units of walking, so stepped collision — though perfectly correct, the riser is under `MAX_STEP_HEIGHT` and it *does* climb — reads as a violent stutter, one hop every 0.27s at `moveSpeed` 3 and every 0.13s sprinting. Meanwhile the average slope is an entirely ordinary 29.4 degrees. Nothing was wrong except the quantisation, which is exactly the case a collision ramp is for. Bonus: 1 volume instead of 20 boxes, and the horizontal stutter goes too (with boxes, the wall pass kept shoving you back off the step two ahead until the ground pass lifted you).
- Ramps alone leave the staircase's **sides** with no collision at all, because the wall pass never sees ramps by design. You could walk straight into the flight from either side and end up inside it. Fixed by giving `steps` two thin authored boxes, one per side, hugging the 3-unit width just outside it. The ends stay open, so walking on from the bottom and off at the landing both still work.
- The right answer turned out to be neither: **fill the staircase's own solid volume**, as nine full-width boxes stepping up under the ramp. Not side walls, which behave as invisible parapets at whatever height you pick, and not a railing, which is a thing you model and which brings its own collider if it is ever added.
- Why boxes for the *mass* don't reintroduce the stutter that made us drop stepped collision in the first place: they are not the walking surface. The ground pass takes the **tallest** standable surface among boxes and ramps, and each box's top is set to the ramp's height at the segment's *lower* end, so within a segment the ramp is always the higher of the two and always wins. The boxes only ever matter horizontally, below the surface you are standing on.
- That same choice, top = height at the lower end, is also what keeps the flight climbable. Walking up, the box ahead has its top at or below your current feet, so `E.yMax <= feetY + MAX_STEP_HEIGHT` holds and the wall pass skips it. Had the tops been set at each segment's *upper* end instead, every segment boundary would have been a wall 0.56 tall against a 0.5 step limit, and the staircase would have been unclimbable by six centimetres.
- The bottom box is capped at **0.4**, below `MAX_STEP_HEIGHT` (0.5), and the margin is the point. It was first set to exactly 0.5, and that made the first step unclimbable: the rule is `E.yMax <= feetY + MAX_STEP_HEIGHT`, so 0.5 against 0.5 is true on paper, but the box's top goes through the instance's world matrix and comes back as 0.50000007, which is greater. The same float noise was visible in the printed extents earlier, where a clean 0 came out as `6.5e-08`. **Never sit a value exactly on a comparison threshold**, especially one that has been through a matrix.
- Result: solid from every side, nothing above the walking surface, so you can walk off the edge and fall the whole nine metres. Which is what a player should be allowed to do.
- Removing the boxes entirely is not an option, and the reason is worth knowing: the ramp's footprint spans the full 3-unit width in model space, so a player who walks into the side with nothing to stop them ends up inside the mesh and is then *lifted onto the surface* by the ground pass. The failure isn't clipping through, it is being teleported up the side of the staircase.
- A `GroundVolume` deliberately isn't a `Collider`. The collision code reads geometry through `getExtents()`, which returns a world-space axis-*aligned* box, so a tilted surface can't survive the trip — even an OOBB comes back out as its fattened envelope. A slope needs a height *function*, not a box. So ramps live in their own list, consulted only by the ground pass; the wall pass never sees them, which is also correct by definition (a ramp is something you walk onto, never something that blocks you). They're evaluated in model-local space via `inverse(Wm)`, where the footprint is axis-aligned whatever the instance's rotation, so unlike every box in the scene a ramp stays exact at arbitrary angles.
- A flat landing is just a ramp whose `rise.from` equals its `rise.to`: same formula, no second concept.
- The numbers came from the mesh, decrypted to measure it (MGCG is AES-128-CBC, key `CG2023SkelKey128`, IV `00..0F`, then the decompressed size as ASCII in the first 16 bytes and raw deflate after it, wrapping an ASCII glTF). `SPW_Medieval_Castle_Steps` is 19 treads of 0.8 with a 0.45 riser plus a flat landing, over 20 x 3 x 9 local units. The ramp is fitted through the *midpoint* of every tread rather than anchored at the front edge: that halves the worst-case error to 0.225, exactly half a riser, which is the best a straight line can do. It's also extended 0.4 past the mesh at both ends so it meets the courtyard floor and the landing with no lip at either end. Verified: max deviation 0.225, height 0.0 where it meets the floor and 9.0 where it meets the landing.

## Vertical view smoothing
- The ground clamp moves the camera up in a single frame whenever the player steps onto something. `eyeStepOffset` absorbs that jump and decays back to zero with a 0.06s time constant, so the *view* eases up while `camPos` stays exact — collisions, gravity and ground contact all keep working on the true position, only what's rendered is eased. This is what Source does for stairs (and Quake with `pm_stepsmooth`).
- Decay is exponential, not linear: it never overshoots, and it needs no "am I still stepping" state, since a continuous climb just settles at a small constant lag instead of oscillating.
- Only *upward* snaps feed it. Smoothing falls too would make gravity feel rubbery.
- Capped at 0.6, past which the view would trail so far under the eyes it reads as sinking, and reset on jump, so jumping right after a step-up doesn't start from a view still trailing behind.
- With the staircase now a ramp it barely fires there. It's what keeps crates, ledges and landings from snapping — which is the general version of the problem the stairs only made obvious.
- Deliberately **no BVH**. `Scene.hpp` can parse `{"type": "BVH", "children": [...]}`, but `CreateColliderRecursive` pushes the BVH's *parent* node into `GlobalColliders` next to its children, and that parent's `getExtents()` returns the union of them all: the archway-filling box, straight back. Filtering the parents out isn't possible from our side either, since `Collider::type` and `::children` are private and only `ColliderShow` is a friend. Authoring leaf boxes ourselves is what keeps the gameplay list flat and usable.
- Scene-authoring gotcha found while testing: the `steps` instance was sitting entirely inside the `keep` instance's auto-fit box (the keep spans world Z -12.5..9.3, the stairs sat at Z 4.5..7.5), so no amount of correct stair colliders would have made it climbable. Moved against the inner face of the west wall instead. Worth remembering that an auto-fit box on a large building silently swallows everything placed near it.

## Cheats / debug toggles
- All debug/cheat flags (`gravityEnabled`, `collisionEnabled`, `jumpEnabled`, `sprintEnabled`, plus the shading ones below) are grouped into one `CheatFlags` struct, held as a single `cheats` member on the app class, instead of being loose booleans scattered among the camera/physics state.
- No persistence on purpose: it's a plain struct with default member initializers, so it just resets to the "legit" defaults (everything `true`, i.e. cheats off) every time the app starts. No config file, no serialization needed.
- Grouping them like this makes them easy to find as a block, easy to reset all at once, and gives a natural place to hang a future debug UI or keybind toggles off of (e.g. iterate/reflect over the struct's fields) without polluting the rest of the class's member list.
- Call sites read through the struct, e.g. `if(cheats.gravityEnabled)`, `if(cheats.collisionEnabled)`, `if(cheats.jumpEnabled)`, `if(!cheats.sprintEnabled || !ctrlHeld)`.
- The numeric tuning behind those cheats (`moveSpeed`, `sprintMultiplier`, `jumpSpeed`, `gravity`) lives in a separate `MovementParams` struct (`movement` member), not in `CheatFlags`. Reasoning: those bools answer "is this cheat on/off", these floats answer "how strong is it", different concern, so a different struct, even though both sit next to each other on the class and follow the same no-persistence pattern.
- Jump does nothing with gravity turned off, on purpose: jump only sets an upward velocity, and that velocity only ever turns into actual movement inside the `gravityEnabled` branch of `GameLogic()`. With gravity off it gets reset to `0` the same frame. Vertical movement without gravity goes through R/F (direct fly up/down) instead.

## Lighting cheats
- The lighting is the part of the project with the most numbers in it and the least to show for a wrong one: a black wall can be a dead light, a normal pointing the wrong way, a material eating everything, or a texture that is simply dark, and all four look identical. The cheat menu now carries nine switches whose only job is to tell those cases apart, in the order you'd reach for them: **Sun**, **Lanterns**, **Spotlight**, **Ambient Light**, **Sun Orbit**, **Specular**, **Tone Mapping**, **Fullbright**, **Show Normals**.
- They split by *where* they act, and the split is the design. Which sources exist is a CPU question, so the first five live in `SceneLights` and are toggled by simply not uploading a light: `update()` returns a filtered copy of the authored list and `lightCount` shrinks with it, so the shader's loop never learns that anything was turned off. How the surviving light is shaded is a GPU question, so the last four are `CheatFlags` bools resolved into one `int debugFlags` on the global uniform.
- One bitmask rather than four separate uniform fields, with the bits named in `LightConstants.glsl` next to `LIGHT_DIRECT`/`LIGHT_POINT`/`LIGHT_SPOT`, so the C++ side and the shader read the same names for the same bits. The bits are independent and combine (Show Normals over a scene with only the lanterns on, say). `debugFlags` slots into the four bytes std140 pads `ambientDir` with, exactly the trick `lightCount` already plays after `eyePos`, so the light array still starts at offset 64 and the uniform does not grow by a single byte.
- The switches for the sources are per light **type**, not per light. The scene has one sun, two deliberately matched lanterns and one spot, so a per-light list would add rows without adding an answer: the question being asked is "is that the sun or a lantern doing that", and the type answers it.
- Two of the four shading bits are inverted against their menu row, on purpose. The rows read **Specular** and **Tone Mapping** and default to `[ON]`, because a cheat row should say what the frame still has, while the flag says what the shader should drop (`LIGHT_DEBUG_NO_SPECULAR`, `LIGHT_DEBUG_NO_TONEMAP`). The inversion happens once, where the mask is built.
- Specular off is not a branch in the BRDF: `k` is the diffuse share, so forcing it to `1` leaves the specular term multiplied by zero and everything else untouched. Tone Mapping off is what makes overexposure visible at all, since the tone map's whole job is to hide it by pulling values back into range; without it, anything above 1 clips to flat white and you can see exactly where.
- Show Normals is placed *after* the `flatNormals` block in the shader, so what it draws is the normal the lighting actually used, faceted faces included. That is the point of having it: the smeared hard edges on the MGCG models were a normals bug, and this is the only view that shows normals directly instead of through three other terms.
- Sun Orbit revives the orbit machinery that `lights.json` parks at `orbitSpeed: 0` (see the shadow-map caveat above) without touching the data: it forces an orbit onto directional lights that were authored static, at a deliberately unnatural 15°/s (a full turn every 24 seconds), because sweeping the sun through every incidence angle in a few seconds is the fastest way to see how the whole castle reacts to one. Lights *with* an authored `orbitSpeed` ignore the switch and keep their own speed. It runs on its own angle accumulator, which only ticks while the switch is on, so turning it on starts from the authored direction and turning it off puts the sun back exactly where `lights.json` wants it rather than leaving it wherever a shared clock had got to.
- Ambient Light off returns a black ambient by **value** from `SceneLights::ambient()` instead of adding a shader flag: both hemisphere colors black leaves the blend between them black whichever way a surface faces, so the shader needs no switch at all. The accessor stopped returning a reference for it, since with the switch off there is no stored object to point at.
- Fullbright and Show Normals return early and skip the light loop entirely; the other switches leave the loop running, which matters because the interesting cases (a light contributing nothing, a highlight sitting where you didn't expect one) only exist while it does.

## Cheat HUD (`CheatHud.hpp` / `UiQuad.hpp`)
- Toggle menu for the cheats above, bound to `L`. Opens/closes on `L`, navigable with Up/Down + Enter or the mouse, freezes the game (camera and physics both) while open.
- Rows are added one by one in `localInit()` and each one holds a `bool*` into the flag it drives, so a row can point at a `CheatFlags` member or straight into another module's public state (the lighting rows point into `sceneLights`). The HUD never owns or copies a value, which is why adding a switch is one `addToggle` line and no plumbing.
- The skeleton's only 2D drawing primitive is `TextMaker` (glyph quads from a font atlas), and there's no filled rectangle in its printable ASCII range. So the toggle rows are plain `TextMaker` text, but the panel background and the selection-highlight bar needed a second, minimal pipeline of our own (`UiQuad.hpp`): flat-colored quads, no textures or descriptor sets, just a push-constant color, modeled directly on how `TextMaker` builds and submits its own pipeline. No changes to `Starter.hpp` anywhere in this feature.
- Mouse look is gated behind holding the left button in `Starter.hpp`'s `getSixAxis`, not a captured cursor, so the mouse was already free to use for HUD hit-testing. The only conflict: `getSixAxis` also reads that same left click as a drag-look input. Fixed by reading the HUD's own click first (see the sticky-mouse-button gotcha below) and, if the HUD is open, zeroing out the `m`/`r`/`fire` values `getSixAxis` returns before they reach the camera.
- `getSixAxis` turns on `GLFW_STICKY_MOUSE_BUTTONS`, which makes `glfwGetMouseButton` a one-shot read: it reports a press once, then reads back as released until the button is physically released and pressed again. Whoever polls the mouse button first each frame gets that one true reading. That's why `hud.update()` is called before `getSixAxis()` in `GameLogic()`, not after.
- Depth test gotcha: `Pipeline::create()` hardcodes depth test and depth write on for every pipeline, with no way to turn it off from outside `Starter.hpp`. The background panel and the highlight bar both sit at `z=0` and overlap on screen, so with the default `LESS` compare op the highlight (drawn second) failed the depth test against the depth the background had just written at that same `z`, and silently never appeared. Fixed with `VK_COMPARE_OP_LESS_OR_EQUAL`, the same fix `TextMaker` already uses for its own overlapping same-z glyph quads.
- Buffer-lifetime gotcha: once a named command buffer is submitted through `BaseProject::submitCommandBuffer`, `Starter.hpp` dereferences its "current" entry unconditionally every frame from then on, with no supported way to detach it and later resubmit under the same name. So `UiQuad` can never just submit "nothing" while the HUD is hidden: it always keeps at least one real (if geometrically empty/unused) quad in its mesh, since `Model::initMesh` also flatly refuses a zero-size buffer.
- Resize gotcha: `CheatHud::renderRows()` converts each row's pixel position into a fixed NDC anchor before calling `TextMaker::print()`. `UiQuad`'s rects stay in pixel space and get reconverted on every mesh rebuild, so they track a resize automatically, but `TextMaker::resizeScreen()` just rebuilds from whatever NDC anchor was already baked in, so text silently stayed positioned for the old window size after a resize. Fixed by having `CheatHud` remember the last screen size it rendered for and force a fresh render (with fresh anchors) whenever that size changes while the HUD is open.
- The panel also fits itself to the window height, which the lighting switches forced: the font's line height is 48px, so at the authored scales fourteen rows plus the title come to ~740px of content in a window that is 600 tall by default, and the bottom rows would simply have been drawn off-screen. There is no scrolling and hit-testing is derived from the same numbers, so an off-screen row is a row that can be neither read nor clicked. `computeLayout()` now measures at the asked-for scales, compares against the room actually available, and if it doesn't fit applies one shrink factor to the text scales and the row heights alike (floored at 0.4, past which the text stops being readable and running off the bottom is the lesser evil). Widths are then measured at the fitted scale, so a shrunk panel is narrower too. The cached layout is invalidated on resize, since the height it was fitted to is now part of it.
- Panel size is computed, not guessed: `CheatHud::computeLayout()` calls `TextMaker::measureText()` to get the actual rendered width/height of the title and of each row's label + `[ON]`/`[OFF]` state, then sizes the background panel to exactly fit that. `measureText` takes a `fontId` rather than the `(FontFace, Bold, Italic, Small)` flags `print()` takes, so `computeLayout()` duplicates `print()`'s own formula for turning those flags into a `fontId`.
